# DataForSEO Keyword Pipeline — Technical Review

Your setup is a good starting point for building an automated competitor keyword research system. The overall architecture makes sense:

1. Define competitor websites and campaign settings.
2. Fetch competitor keywords through DataForSEO.
3. Save individual competitor datasets.
4. Merge the datasets.
5. Remove duplicates.
6. Sort by keyword difficulty and search volume.
7. Export CSV files.
8. Automatically commit the results to GitHub Actions.

However, I would not move this into production just yet. There are several issues worth addressing, particularly around keyword relevance, API response validation, CSV integrity, and how you interpret keyword difficulty.

The most important distinction is that your pipeline currently retrieves keywords associated with competitor websites. It does not necessarily retrieve keywords relevant to dental marketing.

That distinction explains why you're seeing results such as:

- `google` — 68,000,000 searches.
- `google do` — 20,400,000 searches.
- `kahoot` — 11,100,000 searches.

These are not necessarily API errors. They indicate that the source domains' keyword datasets contain terms that are not useful to your dental agency.

Let's examine the setup.

## 2. Critical issue: Your keyword difficulty extraction is incorrect

High priority — fix before production

I inspected your uploaded `storage.js` and `fetcher.js`.

In `storage.js`, you currently have:

```
const difficulty = item.keyword_difficulty || 0;
```

You also use:

```
const diffA = a.keyword_difficulty || 0;
```

in your sorting logic.

The problem is that DataForSEO's Google Keywords for Site response exposes keyword difficulty under:

```
item.keyword_properties.keyword_difficulty
```

It is not a top-level `keyword_difficulty` field in this endpoint's documented response structure.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.dataforseo.com\&sz=32)

DataForSEO API v.3+1



Consequently, your current implementation will likely assign `0` to almost every keyword.

That creates a serious problem:

- All keywords may be classified as easy.
- Your difficulty sorting becomes ineffective.
- Your medium and hard CSV files may be empty.
- Your SEO prioritization becomes unreliable.

My recommendation: Create a single helper function and use it everywhere.

```
export function getDifficulty(item) {
  return item.keyword_properties?.keyword_difficulty ?? null;
}
```

Then update your sorting:

```
items.sort((a, b) => {
  const diffA = getDifficulty(a) ?? 101;
  const diffB = getDifficulty(b) ?? 101;

  if (diffA !== diffB) return diffA - diffB;

  const volA = a.keyword_info?.search_volume ?? 0;
  const volB = b.keyword_info?.search_volume ?? 0;

  return volB - volA;
});
```

And your CSV extraction:

```
const difficulty =
  item.keyword_properties?.keyword_difficulty ?? '';
```

I recommend using an empty value rather than `0` when difficulty is unavailable. Zero is a legitimate difficulty score, whereas missing data should remain missing.

## 3. Your competitor keyword relevance problem

High priority

This is arguably the biggest SEO issue.

Your current competitors are:

- pulsedigital.health
- distributedigital.co.uk

You are targeting UK dental practices.

The DataForSEO Keywords for Site endpoint uses relevance-based keyword discovery. It does not promise that every returned keyword is commercially relevant to your business.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.dataforseo.com\&sz=32)

DataForSEO API v.3



For example, a competitor could have a page, backlink profile, or topical association that causes unrelated keywords to appear in its dataset.

I would introduce a keyword qualification stage.

Suggested filtering architecture:

Stage 1: Raw keyword collection

Collect all 500 returned keywords per competitor.

Stage 2: Relevance classification

Identify keywords associated with dental practices, dental services, and dental marketing.

Stage 3: Commercial intent classification

Identify keywords with agency, service, lead-generation, or purchasing intent.

Stage 4: Qualified keyword database

Retain relevant keywords and their original metrics.

For your agency, I would start with these keyword categories:

| Category                   | Example keywords                    |
| -------------------------- | ----------------------------------- |
| Dental marketing           | dental marketing agency             |
| Dental SEO                 | dental SEO services                 |
| Dental PPC                 | Google Ads for dentists             |
| Dental website development | dental website design               |
| Patient acquisition        | get more dental patients            |
| Local SEO                  | local SEO for dentists              |
| Dental reputation          | dental reputation management        |
| Dental social media        | social media marketing for dentists |

One important distinction: do not simply delete every keyword that lacks the word "dental".

For example, `Google Ads agency` could be commercially relevant even without the word dental. It needs further qualification rather than automatic rejection.

I would preserve the original raw files and create separate qualified datasets.

## 4. Review of your fetcher.js

Your uploaded `fetcher.js` is relatively clean, but I see five areas to improve.

### A. API response validation

You currently check:

```
if (response.ok) {
  const data = await response.json();
}
```

This checks HTTP success, not whether DataForSEO successfully processed the request.

You subsequently check individual task status, which is good, but you should also validate the top-level response.

For example:

```
const data = await response.json();

if (data.status_code !== 20000) {
  throw new Error(
    `DataForSEO error: ${data.status_message}`
  );
}
```

Also check `task.status_code` and `task.result` separately.

### B. Missing API error details

Your current code logs:

```
console.warn(
  `Task failed for ${targetUrl}: ${task?.status_message}`
);
```

This is useful, but I would also log the status code and target.

That makes troubleshooting much easier when you have multiple competitors.

### C. Missing timeout handling

Your fetch request has no timeout.

I recommend:

```
signal: AbortSignal.timeout(60000)
```

This prevents an API request from hanging indefinitely.

### D. Missing pagination

You have:

```
limit: settings.limit
```

with a limit of 500.

This means you retrieve at most 500 keywords in that request.

DataForSEO returns `total_count` and an `offset_token` for subsequent results. Your current fetcher does not use pagination.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.dataforseo.com\&sz=32)

DataForSEO API v.3



For your initial implementation, 500 per competitor is reasonable.

However, if you eventually want a more comprehensive competitor database, implement pagination and make the maximum number of pages configurable.

### E. Missing rate and cost monitoring

DataForSEO returns task-level cost information.

I recommend logging:

- Competitor domain.
- Number of keywords returned.
- API task status.
- Request cost.
- Total pipeline execution time.

This will become particularly useful when you expand from two competitors to 20 or 50.

## 5. Your storage.js needs some improvements

I found three additional issues.

Issue 1: CSV escaping

You currently wrap keywords in quotation marks:

```
const keyword = `"${item.keyword || ''}"`;
```

But if a keyword contains quotation marks, they are not escaped.

A safer implementation:

```
function escapeCsv(value) {
  const str = String(value ?? '');
  return `"${str.replace(/"/g, '""')}"`;
}
```

You should also apply CSV escaping to every field, not just the keyword.

Issue 2: Stale CSV files

Your current storage implementation skips writing a file if its dataset is empty.

For example:

```
if (data.length === 0) return;
```

Imagine yesterday's pipeline generated 200 easy keywords.

Today, the pipeline generates zero easy keywords.

The old CSV remains in your repository and could be mistaken for today's results.

I recommend ensuring that every pipeline run produces a fresh output, even if the file contains only headers.

Issue 3: Difficulty classification

Your thresholds are:

| Classification | Difficulty |
| -------------- | ---------- |
| Easy           | 0–30       |
| Medium         | 31–69      |
| Hard           | 70–100     |

These are perfectly reasonable operational buckets for your own workflow.

However, they are not guaranteed ranking probabilities. DataForSEO describes keyword difficulty as a logarithmic 0–100 metric based on factors including the backlink profiles of the top-ranking pages.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.dataforseo.com\&sz=32)

DataForSEO API v.3



Also, distinguish:

- `keyword_info.competition`: Google Ads competition.
- `keyword_properties.keyword_difficulty`: Organic SEO ranking difficulty.

They measure different things.

Do not use paid competition as a substitute for organic keyword difficulty.

### Sandbox versus live

Your fetcher correctly switches API hosts:

```

  ? 'https://api.dataforseo.com'
  : 'https://sandbox.dataforseo.com';
```

This is the right approach.

However, there is something important to understand about DataForSEO Sandbox.

Important

Sandbox responses contain dummy data. They are useful for testing the API integration and response structure, but they are not representative of actual keyword research results.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.dataforseo.com\&sz=32)

DataForSEO API v.3+1



Therefore:

- Sandbox: test your code, API authentication, response parsing and CSV generation.
- Live: retrieve actual UK keyword datasets.

Do not use sandbox results to evaluate the quality of your competitor keyword research.

### One additional recommendation: API-side filtering

Your fetcher currently sends no filters or explicit sorting instructions.

DataForSEO supports both.

I would consider adding:

```
const payload = [{
  target: targetUrl,
  location_name: settings.location_name,
  language_name: settings.language_name,
  limit: settings.limit,
  include_subdomains: settings.include_subdomains,
  include_serp_info: settings.include_serp_info,

  order_by: [
    "relevance,desc",
    "keyword_info.search_volume,desc"
  ]
}];
```

This is useful because DataForSEO supports relevance-based sorting, with relevance as its default sorting principle.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://docs.dataforseo.com\&sz=32)

DataForSEO API v.3



You should prioritize relevance before search volume. Otherwise, you risk allowing enormous but irrelevant search terms to dominate your research.

I would initially avoid aggressive API-side keyword filtering. Preserve the original dataset and apply your own relevance classification afterward.

## 7. Review of your GitHub Actions workflow

Your workflow is a good idea. Automating the entire process means you can periodically refresh competitor datasets without manually running your machine.

However, check the following.

### A. YAML syntax

As pasted, you have:

```
workflow_dispatch: *# Allows you to run it manually
```

And:

```
contents: write *# Crucial...
```

If these characters are actually present in your YAML file, they will cause parsing errors.

They should be:

```
workflow_dispatch: # Allows manual execution
```

And:

```
permissions:
  contents: write # Allows repository commits
```

If the asterisks were only introduced by copying the code into ChatGPT, disregard this particular warning.

### B. Dependency installation

You currently use:

```
- name: Install dependencies
  run: pnpm install
```

I recommend:

```
- name: Install dependencies
  run: pnpm install --frozen-lockfile
```

This ensures GitHub Actions uses the dependencies recorded in your lockfile instead of silently resolving different versions.

Also make sure your `package.json` contains:

```
{
  "type": "module"
}
```

Your JavaScript uses ES module imports and exports.

### C. Git commit and push

Your current approach is reasonable:

```
git add storage/
git commit -m "Add generated keyword CSVs" || echo "No changes to commit"
git push
```

A few considerations:

- Your workflow needs write permission to the repository.
- Branch protection rules must permit the bot to push.
- Concurrent workflow executions could produce Git push conflicts.
- Consider adding GitHub Actions concurrency controls.

One positive point: GitHub's automatically generated `GITHUB_TOKEN` does not normally trigger another `push` workflow when the bot pushes its commit. You do not need to worry about an automatic infinite execution loop with this configuration.

### D. Scheduling

Currently, your workflow executes on:

- Push to `main`.
- Manual execution.

For an SEO research pipeline, I would also introduce a scheduled refresh.

For example, weekly:

```
schedule:
  - cron: '0 3 * * 1'
```

This runs every Monday at 03:00 UTC.

Remember that GitHub scheduled workflows use UTC, and execution can be delayed during periods of high GitHub Actions load.

I would not refresh competitor keyword datasets every day initially. Weekly or fortnightly is a sensible starting point.

## 9. My recommended production architecture

I would make one significant improvement to your overall system: introduce a keyword intelligence layer between data collection and CSV export.

## Recommended architecture

1. Configuration

   Competitors, location, language, API environment and collection limits.
2. Data collection

   DataForSEO Keywords for Site API, with pagination and error handling.
3. Raw data storage

   Preserve each competitor's untouched API keyword records.
4. Data normalization

   Normalize keyword text, extract metrics, handle missing values and deduplicate.
5. Keyword intelligence

   Classify relevance, search intent, topic and commercial value.
6. Keyword prioritization

   Calculate priority scores using difficulty, volume, relevance and commercial intent.
7. CSV exports

   Generate separate datasets for raw keywords, qualified keywords, easy opportunities, medium opportunities and hard opportunities.
8. GitHub automation

   Commit updated datasets and preserve historical snapshots where useful.

### Suggested final CSV structure

I would expand your current five columns to something like this:

| Column             | Purpose                                                |
| ------------------ | ------------------------------------------------------ |
| Keyword            | Search query                                           |
| Search Volume      | Monthly search volume                                  |
| CPC                | Cost per click                                         |
| Paid Competition   | Google Ads competition                                 |
| Keyword Difficulty | Organic difficulty                                     |
| Search Intent      | Informational, commercial, transactional, navigational |
| Topic              | Dental SEO, PPC, website design, etc.                  |
| Relevance          | Relevant, partially relevant, irrelevant               |
| Competitor Sources | Domains associated with keyword                        |
| Priority Score     | Your calculated opportunity score                      |

This gives you something much more useful than a simple keyword list: a dataset you can use to make SEO campaign decisions.

Pipeline A: Competitor research

Research websites belonging to dental marketing agencies.

Examples of keyword opportunities:

- Dental SEO agency.
- Dental marketing company.
- Dental PPC agency.

Research actual dental practices and their competitors.

Examples of keyword opportunities:

- Emergency dentist in Manchester.
- Invisalign dentist in Birmingham.

These are two very different SEO markets.

Keeping the datasets separate will make your keyword research substantially more useful.
